# Memory & Context

This file contains crucial context, learned rules, and past experiences that agents MUST adhere to when working within the Syncoboard monorepo.

## 1. Testing Strategy

* **Unit Testing `ApiClient`:** When unit testing subclasses of `ApiClient` using `bun:test`, do not spy on inherited protected methods directly (e.g., `spyOn(instance, 'post')`) as it bypasses `baseURL` configuration. Do not manually override the internal `client.defaults.adapter` as it is brittle and fails in CI. Instead, use `axios-mock-adapter`. Safely access the protected Axios instance via an `unknown` cast: `const client = (instance as unknown as { client: AxiosInstance }).client; const mock = new MockAdapter(client);`
* **Test File Locations:** Tests for `src` directories across the monorepo (e.g., `apps/web`, `services/webhook`) are conventionally located in a package-root `__tests__` directory mirroring the internal path structure. However, the `packages/api` package deviates from this convention and places its tests inside `packages/api/src/__tests__`.
* **Mocking Prisma:** When mocking Prisma in `bun:test`, use `mock.module("@syncoboard/db", () => ({ prisma: { model: { method: mock() } } }))` globally. To assign the mock to a typed variable without triggering `@typescript-eslint/no-explicit-any`, cast it via `unknown` (e.g., `db.prisma as unknown as typeof prismaMock`). Call `.mockClear()` on specific mocked methods in `beforeEach` to reset state between tests.
* **Mocking Loggers:** In test files (e.g., `bun:test`), mock or spy on the centralized `logger` from `@syncoboard/shared` (e.g., `logger.error = mock()`) instead of the global `console.error` when validating error logging behavior.
* **Testing `ApiClient` Domains:** In non-browser environments (like `bun:test`), `ApiClient` automatically prepends an absolute base (e.g., `http://localhost`, `API_URL`, or `NEXT_PUBLIC_API_URL`) to relative URLs. When testing `ApiClient` subclasses, ensure mocks or assertions account for this absolute URL conversion (e.g., expect `http://localhost/api/...` or use regex matching like `/\/api\/...$/`) to prevent brittle CI failures across different environments.
* **Webhook Board Mocking:** When mocking the Prisma `Board` model in `services/webhook` tests, ensure the mocked object includes `isActive: true` (e.g., `prismaMock.board.findFirst.mockResolvedValueOnce({ id: '...', isActive: true })`); otherwise, the handler will early-exit due to inactivity checks and cause downstream test assertions to fail.
* **Performance Testing:** Use standalone scripts running via Bun to establish performance baselines. Files executed with `bun test` must contain `.test`, `_test_`, `.spec`, or `_spec_` in their filename. When using `bun:test` mocks and timers to simulate DB latency in benchmarks, avoid strict time-based assertions (like `expect(a).toBeLessThan(b)`) as event loop jitter with parallel promises can cause unpredictable execution times and flaky CI failures.
* **Next.js Server Components Testing:** When executing tests with `bun test` for modules or packages that incorporate `import "server-only";`, you must append the `--conditions react-server` flag (e.g., `bun test --conditions react-server`) to prevent the tests from throwing a Client Component import error.
* **Mocking Environment Variables:** In `bun:test`, when mocking environment variables, cloning via `const originalEnv = process.env` is insufficient because it creates a reference. Use spread syntax (`{ ...process.env }`) to snapshot and restore the environment variables between tests.

## 2. Environment & Execution

* **Next.js Build Vars:** Next.js applications in the monorepo (e.g., `apps/web` and `apps/dashboard`) require environment variables like `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_GITHUB_APP_NAME` to build, and `AUTH_SECRET` to start locally without MissingSecret errors. To bypass this during local builds, pass dummy values inline (e.g., `cd apps/dashboard && NEXT_PUBLIC_API_URL="http://localhost:3000/api" NEXT_PUBLIC_GITHUB_APP_NAME="dummy" AUTH_SECRET="dummysecret" bun run build`).
* **Dependency Installation:** Always ensure dependencies are installed by running `bun install` before executing tests or build commands, as missing packages (like `axios`) can cause immediate module resolution failures.
* **Bun Test Execution:** Running a global `bun test` in the monorepo root may cause a segmentation fault in Bun. Always run tests scoped to specific packages or directories (e.g., `bun test packages/api/`). Also, when running specific test files with `bun test`, prefix the path with `./` (e.g., `bun test ./packages/shared/__tests__/serialize-bigint.test.ts`) to avoid "filters did not match" errors. Ensure filenames contain `.test`, `_test_`, `.spec`, or `_spec_`.
* **Prisma Formatting:** When formatting Prisma schema files (`schema.prisma`), use `bun x prisma format` instead of Prettier, as the project's Prettier configuration does not infer the Prisma parser.
* **Running Next.js Linter:** To run the linter in the Next.js `apps/web` project, use `bun run lint` (which executes standard ESLint) instead of `bun x next lint`, as the latter may fail with an invalid project directory error. To run lint checks across all workspace packages and verify strict type-checking adherence, use `bun run --filter "*" lint`.
* **Prisma Generation Context:** When running Prisma commands locally inside `packages/db`, `bun run generate` may fail to resolve inline environment variables. Explicitly use `DATABASE_URL="..." bun x prisma generate` or `DATABASE_URL="..." bun --filter @syncoboard/db generate` to ensure Prisma correctly picks up the connection string.
* **Code Formatting:** CI enforces code formatting using Prettier. Since global check scripts may fail locally (e.g., 'Script not found'), always verify and fix code style directly using `bun x prettier --check <file>` or `bun x prettier --write <file>` before submitting changes.
* **Next.js Dev Server Cleanup:** When testing locally, orphaned Next.js dev server processes (`next-server`, `postcss`) may persist and cause `EADDRINUSE :::3000` errors. To fully clean up the port, find the leftover process IDs via `ps -ef | grep next` and terminate them with `kill -9`.
* **Local Postgres Database:** If the local PostgreSQL database is unreachable during Next.js startup, spin up a local instance using Docker: `docker run -d --name postgres -p 5432:5432 -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=syncoboard postgres:15`.

## 3. Architecture & Domain Logic

* **WebRTC Voice Calls:** WebRTC voice call signaling (join, leave, and signal exchange) is handled via the existing `websocket` service (`services/websocket`) using Socket.io events rather than REST API endpoints or database persistence.
* **Subscription Checkouts:** The subscription checkout route (`apps/web/src/app/api/subscriptions/checkout/route.ts`) gracefully handles stale `providerPlanId` values caused by environment transitions (e.g., Sandbox to Production). Client-side subscription checkouts are handled by calling `subscriptionApi.checkout(priceId)` from `@syncoboard/api`, which leverages the `@syncoboard/payment` provider (PayPal). The application must redirect the user to the returned `approvalUrl` (`window.location.href`).
* **Active Subscriptions Validation:** When validating active subscriptions (e.g., preventing duplicate enrollments), use the `hasValidSubscription` utility to verify that the subscription is both 'ACTIVE' and its `currentPeriodEnd` is in the future, as expired trials may retain an 'ACTIVE' status.
* **Subscription Intervals:** The `Price` model defines subscription periods using both `interval` and `intervalCount`. These must be accurately passed to the PayPal provider (`packages/payment`). 'LIFETIME' intervals are mapped to `interval_unit: 'YEAR'`, `interval_count: 1`, and `total_cycles: 100` to comply with PayPal's strict maximum limits for yearly billing intervals.
* **API BigInt Serialization:** When returning database models containing `BigInt` fields (e.g., Task IDs) from Next.js API endpoints, use the `serializeBigInt` utility from `@syncoboard/shared` before passing the data to `NextResponse.json()` to avoid serialization errors.
* **In-Memory Caching in API:** In Next.js API routes, module-level variables (e.g., `let cachedValue = null;`) can be used as a simple in-memory cache to prevent redundant database queries for static data across invocations within the same server instance.
* **Next.js 15 Async Params:** In Next.js 15 route handlers, pages, and layouts, `params` and `searchParams` are asynchronous. They must be typed as Promises (e.g., `params: Promise<{ id: string }>`) and explicitly `await`ed before destructuring.
* **Webhook Board Inactivity:** In the GitHub webhook handler (`services/webhook`), incoming events for inactive boards (`isActive: false`) are intentionally ignored by returning an HTTP 200 response with `{'message': 'Ignored: Board is inactive'}`. The system assumes a strict one-to-one mapping between GitHub repositories and boards.
* **Next.js Server Actions Errors:** To prevent unhandled Server Action errors from bubbling up as 500 Internal Server Errors, actions should return error objects (e.g., `{ error: string }`) for expected logical rejections rather than throwing exceptions.
* **Security - Admin Authentication:** Admin authentication uses `HttpOnly` cookies (`adminToken`) managed by the `apps/web` API. The `packages/api` Axios client requires `withCredentials: true` to transmit these cookies across origins, and frontend applications verify session state via an `/auth/me` endpoint.
* **Security - Role Hierarchy:** The application uses a hierarchical Role enum (`ADMIN`, `MODERATOR`, `MEMBER`) for Workspace and Board members. Task creation, modification, and deletion are strictly restricted to `ADMIN` and `MODERATOR` roles.
* **Security - Proxy Validation:** To prevent IP spoofing when resolving the client IP from the `X-Forwarded-For` header, validate against `process.env.TRUSTED_PROXIES`. Iterate from right to left, skipping trusted proxy IPs, and return the first untrusted IP.

## 4. UI & React Conventions

* **Drag-and-Drop:** The project utilizes `@hello-pangea/dnd` as the standard library for implementing drag-and-drop functionality within React components.
* **Recharts - Zooming:** When implementing interactive zoom functionality in `recharts` (e.g., `AreaChart`) using a categorical axis (`type="category"`), do not use the `domain` property to control the zoom view. Instead, slice the underlying dataset based on the selected range indices and render the chart dynamically using the sliced data.
* **Recharts - Default Library:** The project utilizes `recharts` as the standard library for rendering data visualizations within the React web application.
* **Toast Notification Usage:** The `showToast` function from `ToastContext` expects the message string as the first argument and the toast type as the optional second argument: `showToast(message: string, type?: ToastType)`.
* **State Synchronization:** When Client Components initialize local state (e.g., pagination) using props fetched from Server Components, include a `useEffect` hook to synchronize the local state with prop changes.
* **Z-Index Hierarchy:** The `apps/web` Dashboard layout establishes a specific z-index hierarchy: Side panels/drawers use `z-[70]`, main Header uses `z-[60]`, global overlays like `CommandBar` sit at `z-[80]`, and internal sub-headers sit at `z-10`.

## 5. Coding Style & General Conventions

* **Temporary Feature Disabling:** When temporarily disabling features or UI elements, comment out the relevant code rather than deleting it to facilitate easy restoration later.
* **Logging Formats:** When logging errors using the Pino `logger`, pass the error object as the first argument and the message string as the second (e.g., `logger.error(error, "Error message")`) to ensure the stack trace is properly structured. Use the configured logger instance imported from `@syncoboard/shared` rather than `console.log` or `console.error`.
* **Data Model - Price Display:** Subscription plan prices (`Price.amount`) are stored in the database as integers representing cents. Divide by 100 before displaying them in the UI.
* **Prisma Case-Insensitive Queries:** Utilize `mode: "insensitive"` inside the `where` clause (e.g., `name: { equals: value, mode: "insensitive" }`) for case-insensitive string queries using Prisma with PostgreSQL.
* **Performance - N+1 Transactions:** To resolve N+1 write patterns for heterogeneous database updates, collect individual promises into an array and execute them via `await prisma.$transaction(updates)`.
* **Performance - Bulk Queries:** Refactor sequential queries inside loops into bulk operations using the `in` operator (e.g., `findMany({ where: { id: { in: ids } } })`) and `updateMany`.
* **Workspace Cleanliness:** Ensure temporary scratchpad scripts are deleted before committing changes and requesting code review to prevent polluting the codebase.

## 6. Workflow / Planning

* **Deep Planning Mode:** Before making any changes or creating an execution plan, always enter a deep planning mode. Ask clarifying questions using `request_user_input` or `message_user` until there is absolute certainty about the user's expectations.
* **Test Suite Verification:** When adding or modifying tests, execution plans must include a step to run the full test suite for the relevant package (e.g., `bun test ./packages/api/`) to verify changes and catch regressions.
* **Pre-commit Routine:** Execution plans must explicitly include steps to run the specific test file AND the entire relevant package's test suite immediately before the pre-commit step. The pre-commit step itself must exactly match the phrasing: "Complete pre-commit steps to ensure proper testing, verification, review, and reflection are done."
* **Specificity Rule:** When submitting execution plans, strictly adhere to the Specificity Rule: plan steps must be clear, direct commands with definitive, actionable instructions. Avoid internal monologue or indecision.

* **Important Note:** User Request Supersedes: Always prioritize the user's current, explicit request over any conflicting information in memory. Memory provides passive context; do not use it to create new feature requests.
